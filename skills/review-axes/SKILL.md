# レビュー観点

指摘の 9 割は「動くか」ではなく次の 5 つで出る。**各観点に手順があり、手順を踏むまで所見を言わない。**

## 1. 語が実装と一致しているか

コメント・description・テスト名・変数名が、実装より**広く**読めるものを探す。狭い場合も同じく誤り。

手順:

1. 差分中のコメントと description から、**限定表現**を機械的に抜く
   `だけ / のみ / 必ず / すべて / 〜順 / 〜のとき / 〜なら`
2. 抜いた 1 文ごとに「**この文が禁じている入力は何か**」を書き出す
3. その入力を実装に当てて、本当に禁じられているか確かめる

落ちやすい形:

- 「最近担当した順」と書いて、実装は「直近 3 か月に届いた行のうち現在の版で担当している件数順」
- 「同点は名前で決める」と書いて、実装は同点に到達しない（配列の位置で比べていた）
- 「〜と同じにしてある」と書いて、揃えた根拠が相手側に無い（相手に検証も無かった）

**「〜と揃えてある」系のコメントは消さない。** 消すと次の人が善意で値を変える。ただし揃っている根拠を実コードで確かめてから書く。

## 2. 主張に観測が伴っているか

「〜だと思う」「壊れるはず」で直させない。**直す前に再現する。**

手順:

1. 不具合を主張するなら、**現行実装で症状を出す**（テスト・runner・実データ）
2. 規模を語るなら**測る**（行数・クエリ数・実行計画）。推定値と実測値を混ぜない
3. 再現しなかったら「再現しなかった」と書く。構造上の懸念として残すのは可、断定は不可

外部（サブエージェント・codex・他の AI）の指摘は**そのまま流さない**。1 件ずつ自分で確かめ、誇張は落として報告する。詳細は `subagent-review`。

## 3. テストが本当に欠陥を捕まえるか

書いた直後に**壊して落ちるか**を確かめる。ここを飛ばすと空洞テストが残る。

手順:

1. 対象の実装を戻す（`git stash push -- <file>` か一時編集）
2. 新しいテストだけを回す
3. **落ちなければテストが悪い**。落ちるまで直す
4. 実装を戻す

空洞になりやすい形:

- `expect(...).to all(eq(1))` — 空配列は真。件数を併せて見る
- `expect { }.not_to raise_error` — 名前が挙動を約束しているなら結果まで見る
- 条件が偶然そろって通る — 別の軸（索引順・登録順）で通っていないか、値を入れ替えて確かめる

1 件の不具合は 1 件のテストで塞がない。**同じ原因を持ちうる兄弟**（同種の列・同種の入力）まで回す形にする。

## 4. 構造で防げるものを検査で防いでいないか

テストを足す前に「**書けなくできないか**」を問う。

寄せ先の優先順:

1. 型・スキーマ（GraphQL enum / TS union / `satisfies`）
2. DB 制約（NOT NULL / unique / 外部キー）
3. モデルの不変条件（validation / callback で兄弟行を整える）
4. テスト

型に寄せると実行時テストが消えることがある。消えたぶんは**削る**（残すと二重管理になる）。

判定の目安:

- 限られた値しか取らないのに `String` で通っている引数・フィールド
- 「ありえない状態」をテストで見張っている箇所（作れなくできないか）
- factory や fixture が本番で起きない状態を作れる（不変条件がモデルに無い証拠）

## 5. 既に同じものが repo にあるか

**書く前に探す。** 再発明はレビューで必ず指摘される。

探す対象と探し方:

| 書こうとしているもの | 探す場所 |
|---|---|
| 検索・絞り込み条件 | `app/models/concerns/` の `*able.rb`、既存の `*SearchQuery` |
| 画面の部品（ページャ・日付表示・トースト） | `shared/components/`、`shared/utils/` |
| 値オブジェクト・定数の集合 | 同種モデルの `Struct.new` / `Data.define` |
| 状態・優先度の語彙 | 統合予定の相手側モデル（この repo なら ATS 求人管理） |

`grep -rn "<やりたいこと>" app/models/concerns app/models packages/*/javascript/shared` を先に走らせる。

**将来同じ表に統合する相手がいるなら、値・語彙・持ち方を今から揃える。** 揃えたことは 1 の規則でコメントに残す。

# 提出前スイープ

差分が出来たら、コミット前にこの順で通す。

1. 限定表現の抽出 → 反証（観点 1）
2. 新テストを壊して落ちるか（観点 3）
3. `String` のまま通している限定値が無いか（観点 4）
4. 再発明していないか（観点 5）
5. 実測が要る主張を残していないか（観点 2）
6. lint / format / 型チェックを**パイプで殺さず** exit code で確認

# 指摘の扱い

## 優先度は実害で決める

網羅と着手は別。挙げた所見は次の 3 つに分ける。

- 直す: 実データ・実運用で症状が出る
- 記録に留める: 構造は不味いが、いま踏めない
- 無視: 意図的な未実装、または運用でカバーされている

「全部直す」を提案しない。**判断材料（症状・条件・頻度）を添えて、切る側に渡す。**

## 変更の前に聞く

レビューで見つけたものを勝手に直さない。**所見の提示と修正の実行を分ける。**

実装中の些末な分岐（命名の揺れ・書き方の選択）はデフォルト案で自走し、採用した案を 1 行宣言する。設計・不変条件の置き場所が変わる分岐は宣言だけで済ませず、判断を仰ぐ。
