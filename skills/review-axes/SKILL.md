# レビュー観点

指摘の大半は「動くか」ではなく次の 8 つで出る。**各観点に手順があり、手順を踏むまで所見を言わない。**

## 1. 語が実装と一致しているか

コメント・description・テスト名・変数名・型名が、実装より**広く**読めるものを探す。狭い場合も同じく誤り。

手順:

1. 差分中のコメントと description から、**限定表現**を機械的に抜く
   `だけ / のみ / 必ず / すべて / 〜順 / 〜のとき / 〜なら`
2. 抜いた 1 文ごとに「**この文が禁じている入力は何か**」を書き出す
3. その入力を実装に当てて、本当に禁じられているか確かめる

落ちやすい形:

- 「最近担当した順」と書いて、実装は「直近 3 か月に届いた行のうち現在の版で担当している件数順」
- 「同点は名前で決める」と書いて、実装は同点に到達しない（配列の位置で比べていた）
- `trackClickXxx` という名前で、実際はクリックではなく表示の記録
- `for_validation` という名前で、やっているのは build。`set_xxx` の中で変換までしている
- `dummy` と名付けた値が、実際は既定値（`default`）
- `ブロック依頼者` と書いて、入るのは企業。`HelpPage` を export して、中身はアイコン
- 定数名が `HELP` と `URL` で揺れている（`HELP_URLS` に寄せる）
- 「フロントエンド／バックエンド」のように、読み手で指す範囲が変わる語（Rails / React と書く）
- コメントが手続きの言い換えになっている（コードを読めば分かることは書かない）
- 表示の語が情報を足していない。並びが大きさ順なのに「大きく／少し」を付ける、確率を隠しているのに順位の根拠を説明しない。言葉を足す前に、位置・長さ・色で伝わっていないかを見る

**「〜と揃えてある」系のコメントは消さない。** 消すと次の人が善意で値を変える。ただし揃っている根拠を実コードで確かめてから書く。

命名に迷ったら、**フレームワーク本体の語彙**（Rails の `latest_*` など）と、この repo の既存の慣習（`XxxContainer` は Xxx をラップしたもの、等）を先に見る。

## 2. 主張に観測が伴っているか

「〜だと思う」「壊れるはず」で直させない。**直す前に再現する。**

手順:

1. 不具合を主張するなら、**現行実装で症状を出す**（テスト・runner・実データ・実ブラウザ）
2. 規模を語るなら**数える**（行数・件数・クエリ数・実行計画）。推定値と実測値を混ぜない
3. 再現しなかったら「再現しなかった」と書く。構造上の懸念として残すのは可、断定は不可
4. 動作確認は**何をどの環境で確認したか**まで書く（stg か本番相当か、どのアプリで開いたか、どのブラウザか）

落ちやすい形:

- 「10 件くらいなので問題ない」と言うが、実データは 4000 件以上ある
- 「たぶん直っている」で再読み込みが要る状態のまま出す
- 画面の確認を「Excel で確認」とだけ書く（実際は表計算ソフトが別物で結果が変わる）
- ロード中・低速回線の挙動を見ずに `disabled` を語る（開発者ツールで回線速度を落として確かめる）

外部（サブエージェント・codex・他の AI・Copilot 等の bot）の指摘は**そのまま流さない**。1 件ずつ一次情報（公式ドキュメント・ライブラリのソース）で確かめ、誤りは根拠を添えて落とす。詳細は `subagent-review`。

## 3. テストが本当に欠陥を捕まえるか

書いた直後に**壊して落ちるか**を確かめる。ここを飛ばすと空洞テストが残る。

手順:

1. 対象の実装を戻す（`git stash push -- <file>` か一時編集）
2. 新しいテストだけを回す
3. **落ちなければテストが悪い**。落ちるまで直す
4. 実装を戻す

空洞になりやすい形:

- `expect(...).to all(eq(1))` は空配列でも真になる。件数を併せて見る
- 期待が `not_to have_content` だけで構成されている（表示側を一度も確かめていない）
- テストが実装と同じ変換関数を使っている（仕様の確認ではなく実装の追認）
- `expect` が消えて操作だけ残っている
- 条件が偶然そろって通る。索引順・登録順に依存していないか、値を入れ替えて確かめる
- 配列の順序を期待している。`WHERE id IN (...)` の返り順は実装依存で、FLAKY の芽になる
- factory・fixture が本番で起きない状態を作れる（不変条件がモデルに無い証拠）
- コールバックで再計算が走り、意図した値がテストデータに入っていない

**どの層で書くかを先に決める。**

| 確かめたいこと | 書く場所 |
|---|---|
| ロジックの分岐・境界・状態遷移 | model spec / 単体テスト |
| API の入出力と権限 | request spec / mutation spec |
| 画面の描画と操作 | フロントエンドのテスト（RTL 等） |
| 「ユーザが求めているものはこれ」というシナリオ | E2E（system spec） |

E2E は健全性の担保ではなくシナリオの記述。**シナリオとして書けないなら E2E は不要。**逆に、GraphQL 側だけ書いてフロント側を書かない（またはその逆）は避ける。既存 spec に足すときは、**その spec が元々何を担保していたか**を読んでから足す。意図の違うものを足すと、後から見た人が方針を読み違える。

1 件の不具合は 1 件のテストで塞がない。**同じ原因を持ちうる兄弟**（同種の列・同種の入力・nil のパターン）まで回す形にする。状態遷移があるなら、遷移の並びを書き出して網羅を確かめる。

## 4. 構造で防げるものを検査で防いでいないか

テストを足す前に「**書けなくできないか**」を問う。

寄せ先の優先順:

1. 型・スキーマ（GraphQL enum / TS union / `satisfies`）
2. DB 制約（NOT NULL / unique / 外部キー / 索引）
3. モデルの不変条件（validation / callback で兄弟行を整える）
4. Linter・生成物のチェック（規約は人の目でなく機械に見せる）
5. テスト

型に寄せると実行時テストが消えることがある。消えたぶんは**削る**（残すと二重管理になる）。

判定の目安:

- 限られた値しか取らないのに `String` で通っている引数・フィールド
- 「ありえない状態」をテストで見張っている箇所（作れなくできないか）
- 「よく読めば分かる」で守らせている規約（Linter で落とせないか）
- `any` / `as any` は型の整合が取れていない兆候であって、抑止ではない
- ぼっち演算子・`|| []` の防御。nil や undefined が来ないなら書かない。書けば「来る」と読まれる
- 標準から外れた低レベル指定（BOM・CRLF・px の直書き）。強い理由が無ければ消す。残すなら理由を書く
- `ActiveModel::Type::Boolean` は明示的な `false` 以外をすべて `true` に変える。API の境界で boolean を受けるなら、boolean 以外は 400 で弾く（型の緩い強制変換を検証の代わりにしない）

## 5. 責務と置き場所が合っているか

**「動くか」ではなく「どこに置くべきか」で最も多く止まる。**

手順:

1. 追加した型・クラス・フックについて、**それが知っていい知識**を 1 行で書く
2. 実装がその 1 行を超えていないか読む
3. 超えていたら、超えた分の行き先（別メソッド・別レイヤ・呼び出し側）を決める

落ちやすい形:

- 共有置き場（`shared/` 等）にロール依存・画面依存の知識が入っている
- 低いレイヤから高いレイヤを呼んでいる（model から service を呼ぶ等）。やるなら理由を残す
- 変換・整形の責務が、出力（CSV / Decorator / hooks）側に溜まって用途ごとに特殊化していく
- 1 つのクラスが、取得・変換・保存・認可を全部持っている
- 実装の詳細に外から直接触っている（グローバルな状態変数・内部カラム名への直接参照）
- 画面のための知識をカスタムフックに入れている（フックは状態の制御に寄せる）
- migration の中でモデルを使っている（将来のモデル変更で壊れる）。backfill は task に分けて段階的に流す
- 認可の書き分けが揃っていない（`ready?` と `authorized?` の混在、リゾルバの増殖）
- ID を引数で受けてメソッド内で `find` している（ローダーで先に解決し、本体は業務ロジックだけにする）
- 運用の入り口（rake・コンソール・バッチ）のために専用クラスや別の絞り込みを作っている。入り口は本体の部品に引数を渡して呼ぶだけで済むべきで、専用の経路が要る時点で本体の設計（対象の定義・時点の扱い）に穴がある。「通常と違うことをしようとしている」と感じたら、それは設計を歪めている合図
- 薄いラッパー。判定は 3 つ: 呼び手が 1 つか／プロトコルの知識（何を送り、応答をどう読むか）を持っているか／他の都合が入り込む余地があるか。全部「無い」なら消し、呼び手が共通部品を直接呼ぶ

置き場所を変えるときは、**プロダクト全体の一貫性**を先に見る。新しいディレクトリを切るなら、既存をそこへ寄せる想定なのかを言い、必要なら運用方針を README に置く。

## 6. 既に同じものが repo にあるか

**書く前に探す。** 再発明はレビューで必ず指摘される。

探す対象と探し方:

| 書こうとしているもの | 探す場所 |
|---|---|
| 検索・絞り込み条件 | `app/models/concerns/` の `*able.rb`、既存の `*SearchQuery` |
| 画面の部品（ページャ・日付表示・トースト・ローディング） | `shared/components/`、`shared/utils/`、共有 UI パッケージ |
| ログイン・共通の前処理 | `spec/support/shared_contexts/`、基底クラス |
| 日付・文字列・集合の操作 | 言語／フレームワークの標準（`ActiveSupport` / `date-fns` / `Map.groupBy`）と既存の依存 |
| 値オブジェクト・定数の集合 | 同種モデルの `Struct.new` / `Data.define` |
| 状態・優先度の語彙 | 統合予定の相手側モデル |

`grep -rn "<やりたいこと>" app/models/concerns app/models packages/*/javascript/shared` を先に走らせる。**基底クラスと既存の shared context も読む**（重複していると「不要そうです」で止まる）。

同じ判断が 2 箇所にあるのは不具合の温床。片方だけ直して漏れる。**まとめられないかを先に検討する。**

外部連携を足すときは、同じ仕組み（Cognito・API Gateway 等）で繋いでいる既存連携を先に 2 つ読み、設定キーの形・クライアントの呼び方・テスト用のスタブ（`spec/support/api_stubs` 等）を揃える。独自の initializer や on/off の旗は、既存が持っていないなら足さない。「なぜ合わせていないか」を聞かれた時点で負け。比べるときは表にする（連携ごとに「HTTP を呼ぶ場所」「サービス層が持つ知識」を書き、浮いているものを探す）。

**将来同じ表に統合する相手がいるなら、値・語彙・持ち方を今から揃える。** 揃えたことは 1 の規則でコメントに残す。

自前で仕組みを組む前に、**プラットフォームの標準機能**で足りないかを見る（GitHub の auto-merge と auto-rebase のラベル、CI の組み込み機能等）。レビューが要らない類の変更（submodule の更新等）に自前の自動化を書くのは再発明。

## 7. 規模と同時実行を見積もったか

手順:

1. 追加したクエリについて、**呼ばれる回数**を書き出す（1 回か、行数ぶんか、フィールドぶんか）。GraphQL の型なら、複数のフィールドが同じ関連・同じ導出値に依存していないかを見る。モデルの更新なら、`after_save` 等のコールバックの連鎖を辿って更新 1 件あたりのクエリ数を数える
2. 実データの件数を数える。件数が伸びる軸（ユーザ数・年数）を 1 つ挙げる
3. 同じ操作が**同時に 2 回**走った場合の時系列を書く

落ちやすい形:

- ループの中で `find_by` / `select` を回している（先に配列を集めて `where` で 1 回にする）
- 一覧の各行から集計メソッドを呼んでいる（メモ化・アソシエーション・バッチ読みに寄せる）
- 同じオブジェクトの兄弟フィールド（`state` と `state_label` 等）が、それぞれ同じ高コストな導出値（`maximum(:id)` → `find`）を計算し直している。行数ぶんの N+1 が 1 行の中で二重になる。導出は 1 回にしてフィールドが共有する
- バルク更新で `update!` を 1 件ずつ回し、`after_save` のコールバックが 1 件ごとに照会と `reload` を発行している（最大 500 件で件数ぶん）。コールバックを経由した暗黙のクエリはコードにループが見えないので、連鎖を読んで数える
- 索引の列順が絞り込みの効きと合っていない
- 毎回トークンを取り直している（有効期限まで持ち回せる）
- 非同期ジョブの完了順が入れ替わると、古い結果が新しい結果を上書きする（要求ごとの ID を持たせて突き合わせる）
- 先に出る PR と後から出る PR で、NOT NULL 制約とデータ投入の順序が逆になる
- 画面のボタンを、先行する非同期処理（ID の取得等）が終わってから無効化している。その間に 2 回目が入ると、同じ集合を 2 本のリクエストが処理する（staging で一意制約に当たった実例）。押した瞬間から止める

今回は許容する、という判断は良い。ただし**許容した根拠（件数・頻度）と、いつ効かなくなるか**を残す。

## 8. 時点が混ざっていないか

予測・集計・比較を扱う変更で使う。入力の時点と答えの時点が混ざると、精度は実際より高く出る。**除外条件で誤魔化さず、時点を設計で持つ。**

手順:

1. 保存する値について「どの時点の情報から作ったか」を列で持てるか問う（`scored_as_of` 等）
2. 集計・評価は、その時点が答えより前の行だけで行う。条件で弾くのではなく、行の属性で選ぶ
3. 「数日以内だけ」「リリースから 60 日待つ」のような制約が出たら、それは設計の穴。安くて統計的に正しい代案（過去分を当時の時点で作り直す等）を先に出す。待たせるのは最後の手段
4. 機械学習の出力を保存するなら、学習データに含まれる期間を採点・評価に混ぜない

落ちやすい形:

- 公開済みのものを毎日採点し直し、入力の履歴に自分の結果が混ざる（予測が実績に寄っていく）
- 「精度」の条件が「公開から 60 日経過」だけで、いつ採点したかを見ていない
- 「なぜ絞るのか」を聞かれて、リークの説明ではなく制約の説明を返す

# レビューを受け取れる形にする

差分が正しくても、読めない形で出すとレビューは止まる。**提出はレビュワーへの入力**として作る。

- **description に、なぜ・やったこと・動作確認・やらないこと**を書く。仕様が途中で変わったならその差分も書く。後から読む人はチケットを見に行かない
- **PR の外で関係者と決めた前提**（「数値の根拠は無いが一旦出して検証する」等）は description に書く。レビュアーは PR しか見ないので、書かないと「その相談はどうなったか」と聞き返される
- **UI が変わるならスクリーンショットか動画**を貼る。貼らないと相手にチェックアウトとビルドをさせることになる。`gh` から直接上げられる（gh 2.100 以降）ので、人に添付を頼まず自分で付ける
  - 本文の中の位置に置く: description に `![一覧の展開行](./tmp/list.png)` と書いておき、`gh pr edit <n> --attach './tmp/list.png#一覧の展開行'` で参照先が上げた画像に書き換わる
  - 末尾に足すだけなら `gh pr edit <n> --attach ./before.png --attach ./after.png`（`gh pr create` / `gh pr comment` も同じ `--attach`。動画も可、1 回 50 件まで）
  - 画像は repo に commit しない。`tmp/` 等の gitignore 済みの場所から上げる
- **動作確認は具体的な操作と期待結果**で書く（「◯◯が正しく動く」ではなく「契約中の Agent で推薦し、企業に通知される」）
- **テンプレートのチェック欄は埋める。** 埋めないと本番事故の確率が上がる
- **CI が緑であることを確認してからレビューを依頼する**
- **レビュー依頼の合図（ラベル・Reviewers・Re-request）を出す。** 通知が飛ばないと待ち時間だけが伸びる
- **コミットは 1 つの意図に 1 つ。** 依存更新とテスト修正、機能追加とリファクタは分ける。後のコミットで前のコミットを直さない
- **コミットメッセージは Why を書く。** 何を変えたかは diff にある
- **レビュー指摘の修正は `git commit --fixup=<hash>` で積む。** 新しいコミットを足すと差分が追えない。マージ前に autosquash する
- **ベースからの遅れを測ってから出す**（`git rev-list --count HEAD..origin/master`）。遅れているならリベースしてから依頼する
- **読み切れない大きさなら分ける。** 「複雑で読み切れなかった」は承認ではない
- 既存機能に影響するリファクタは、機能追加より**前**に単独で出す
- **PR の順序は依存の向きで決める。** 結果を読むだけの消費側（優先度付け・画面）は最後。土台（保存・採点）が先
- **スタックにして、各 PR の差分をその PR の分だけにする**（`gh stack`）。base を master に揃えて「下がマージされたら差分が減る」と言い訳しない
- **まだどこにもリリースしていないなら、マイグレーションを積み上げない。** 作成マイグレーションに畳む
- **分けたら、分けた本数ぶんの description を現状に合わせて書き直す。** 1 本だけ直して残りを古いまま置かない

# 妥協と決めを残す

その場の最適が将来の負債になるとき、**何を妥協したか**が残っていないと振り返れない。

- データの実 ID・固定値に依存する実装は、王道（属性を持たせる等）を書いた上で、そうしない理由（コスト・速度・負債になる確率）を書く
- 一時的な回避（ライブラリ内部への当て込み・パッチ）には**出口**を書く。「一生面倒を見る」のか「いずれ差し替える」のかを決める
- 設計方針がレビュー中に大きく振れたら、**なぜ振れたか**を書く。振れ幅が大きいほどリリース後の考慮漏れが出る
- 経緯は文章より **blame で辿れること**が大事。意図があるなら、意図をコードの近くに置く

# 指摘の扱い

## 温度感をラベルで示す

所見の頭に温度感を書く。書かないと、直さなくていいものに時間を使わせる。

- `[must]` 直してから出す
- `[imo]` こうしたい。判断は相手
- `[nits]` 好み。直さなくてよい
- `[ask]` / `[q]` 意図を知りたい。修正要求ではない
- `[good]` 良かったところ

**意図の確認と修正の要求を混ぜない。** 「教えてください」と書いたなら、返ってきた意図が妥当なら引き下がる。

## 優先度は実害で決める

網羅と着手は別。挙げた所見は次の 3 つに分ける。

- 直す: 実データ・実運用で症状が出る
- 記録に留める: 構造は不味いが、いま踏めない
- 無視: 意図的な未実装、または運用でカバーされている

「全部直す」を提案しない。**判断材料（症状・条件・頻度）を添えて、切る側に渡す。**

## 変更の前に聞く

レビューで見つけたものを勝手に直さない。**所見の提示と修正の実行を分ける。**

実装中の些末な分岐（命名の揺れ・書き方の選択）はデフォルト案で自走し、採用した案を 1 行宣言する。設計・不変条件の置き場所が変わる分岐は宣言だけで済ませず、判断を仰ぐ。

## 判断は粒度を揃えて言い切る

設計の議論で複数の論点が出たら、同じ粒度の表にして「消す／残す／変える」を 1 語で書く。「〜も検討」「保留」を混ぜた列挙は、読む側に判断を押し戻している。1 つの論点だけ深掘りして残りをぼかすのも同じ（「はっきりしろ。粒度を揃えて議論しろ」と言われる）。

## 「それで足りるか」は範囲を確かめてから答える

「1 行で足りるか」と聞かれたら、その 1 行が触る集合の範囲（含まれるもの・含まれないもの）を実装で確かめてから答える。バッチの対象が「公開中」だけで「終了済み」を含まないなら、「過去分も全部」の要望には足りない。「ちゃんと考えて」と言われるのはここ。

## 言葉を選ぶ

- 「問題ないですか」「正しいですか」と聞かない。**何を確かめたいのか**を書く（「一般的に取られている手法ですか」「チームの慣例と一致していますか」）
- 分からないものは分からないと言う。曖昧なまま通すより速い
- レビューは理解と価値観を揃える場でもある。**AI に答えさせた文章をそのまま返さない**。自分の言葉で書く

# 提出前スイープ

差分が出来たら、コミット前にこの順で通す。

1. 限定表現の抽出 → 反証（観点 1）
2. 新テストを壊して落ちるか。テストの層は合っているか（観点 3）
3. `String` / `any` のまま通している限定値が無いか。防御の `&.` `|| []` が要るか（観点 4）
4. 追加した型・クラスが知っていい知識を 1 行で書けるか（観点 5）
5. 再発明していないか。同じ判断が 2 箇所に無いか（観点 6）
6. ループ内クエリ・同時実行・PR 間の順序（観点 7）
7. 実測が要る主張を残していないか（観点 2）
8. lint / format / 型チェックを**パイプで殺さず** exit code で確認
9. description・スクショ・確認手順・コミット粒度・fixup・CI 緑（レビューを受け取れる形にする）
10. 予測・集計を触ったなら、入力の時点と答えの時点が混ざる行が無いか（観点 8）
11. 外部連携なら、既存の同種連携と設定・呼び方・スタブが揃っているか（観点 6）
